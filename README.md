# KIPL Website

Marketing site for Kainsara Infraprojects Pvt Ltd (KIPL).

## Structure

```
site/
├── frontend/          static site — HTML/CSS/JS, no build step, no dependencies
│   ├── index.html
│   ├── css/
│   ├── js/
│   └── assets/images/
├── backend/           CMS server + admin panel (Node/Express) — see "Admin panel & CMS"
└── docs/              reference material, not served to visitors
    ├── kipl-profile.pdf
    ├── brand/         original brand assets (logo)
    └── source-images/ full-resolution originals behind frontend/assets/images/,
                        kept for future re-processing (recrop, higher-res export, etc.)
```

**`frontend/`** is the entire current website — plain HTML/CSS/JS, no bundler,
no npm dependencies. It's a complete, self-contained static site: point any
static file server or CDN at this folder and it works as-is.

**`docs/`** holds source material that isn't part of the served site: the
company profile PDF, the original brand logo file, and full-resolution
originals of every processed image in `frontend/assets/images/` (hero
photography, client logos, team headshots) — each named to match its
processed counterpart (e.g. `docs/source-images/hero/hero-01-original.png`
→ `frontend/assets/images/hero/hero-01.jpg`,
`docs/source-images/team/somnath-naik-original.jpeg` →
`frontend/assets/images/team/somnath-naik.jpg`) so it's obvious which
source produced which asset if it ever needs reprocessing at a different
size or quality. To reprocess a headshot after swapping in a new source
photo: drop the new original at its `docs/source-images/team/<slug>-
original.*` path, then resize/flatten/export it to
`frontend/assets/images/team/<slug>.jpg` (JPEG, quality 85, capped at
700px wide) — see recent commit history for the one-off Pillow script
used so far, there's no standing build step for this.

**`backend/`** is the content-management server and admin panel — see
[Admin panel & CMS](#admin-panel--cms) below. The `frontend/` folder is still
a complete static site on its own; the backend simply fills its content
regions (projects, services, team, figures, contact details…) from the
database and serves the `/admin/` panel.

## Admin panel & CMS

`backend/` is a small Node/Express app (no build step). It loads the static
pages from `frontend/`, fills their content regions from a JSON database, and
serves the admin panel at `/admin/`. The static HTML stays the single source
of truth for markup, classes, icons and animation hooks — the CMS only
supplies words, numbers and images — so nothing about the design changes.

### Run it

```bash
cd backend
npm install
# create the three starting accounts (passwords come from the environment,
# never from a file in the repo):
KIPL_OWNER_PASSWORD=… KIPL_EDITOR_PASSWORD=… KIPL_HR_PASSWORD=… npm run seed:users
npm start          # http://localhost:4000/  and  http://localhost:4000/admin/
npm test           # 60 tests: auth, roles, draft/publish, rendering, media, spam, backups
```

The first start installs the starting content (a copy of what the static
site shows today, generated by `npm run seed:content`). Usernames are
`owner`, `editor` and `hr`. Everyone is prompted to choose their own password
on the dashboard; accounts can be added/disabled by the Owner under
**Accounts**. Forgotten Owner password: re-run `seed:users` with
`-- --reset owner` and `KIPL_OWNER_PASSWORD` set.

### Draft → publish

Edits are saved as **drafts**; visitors only ever see the **published** copy.
Use *Preview* (top bar) to see drafts rendered in the real pages. Each item
can be published, discarded back to what's live, scheduled for a future
time, or rolled back to any of its last 20 published versions. Deleting a live
item takes effect on the next publish. Two people editing the same item are
protected by a conflict check.

### Security notes

- Passwords are stored as bcrypt hashes; sign-in is rate-limited and locks
  after 5 failures; sessions are HttpOnly, SameSite=Strict, server-side and
  revocable; state-changing requests also need a custom header + same-origin
  check. Changing a password signs out every other device.
- Content is always inserted as text (never raw HTML); uploads are decoded and
  re-encoded with `sharp` (so EXIF/GPS is stripped and fake images fail);
  SVG is not accepted.
- The contact form is protected by a honeypot field, a minimum-fill-time
  check, link-stuffing detection and a per-IP rate limit. Suspected spam is
  stored in a separate "Spam" tab so a false positive is never lost.
- Not included: two-factor sign-in and email notifications for new
  enquiries (no mail server is configured). Run behind HTTPS in production and
  set `TRUST_PROXY=true` when behind a proxy.

### Data, backups and hosting

Everything lives in `backend/data/` (git-ignored): `db.json` (content, users,
audit log, enquiries), `uploads/` (images) and `backups/` (an automatic daily
JSON backup, last 14 kept). Back up `db.json` **and** `uploads/`. Set
`KIPL_DATA_DIR` to keep data outside the code folder.

The admin needs a host that can run Node **and** keep files on disk (a VPS,
Render/Railway/Fly with a persistent disk, …) — Vercel's serverless
functions can't persist `data/`. Two ways to run the public site:

1. **Node serves everything** (simplest): point the domain at the backend; it
   serves the site and `/admin/` together, and the contact form posts
   enquiries straight into the inbox.
2. **Static export** for a static host: `npm run export:static` renders the
   published content into `backend/dist/` (pages + assets + uploads); deploy
   that folder. Re-export after each publish. On a static host the contact
   form falls back to opening the visitor's email app.

#### Free workflow: admin on your PC, public site on Vercel

No server hosting needed. The admin runs only on your own computer; the public
site stays on Vercel and is rebuilt from a committed copy of your published
content.

1. `cd backend && npm start`, open `http://localhost:4000/admin/`, edit, and
   **Publish** (drafts stay private).
2. Run **`npm run publish:site`** in `backend/`. It saves the published
   content and the uploaded images it uses into `site-content/`, commits that
   folder and pushes. (`-- --no-push` commits only; `-- --no-git` just writes
   the files.)
3. Vercel runs the build in `vercel.json` (`export-static.js --snapshot
   ../site-content`), which renders the pages from `site-content/`, and
   deploys. If a build ever fails, Vercel keeps serving the last good version.

Notes: your database (`backend/data/`) lives only on your PC — back it up
(Backups & export). Make sure `git config user.email` is your GitHub email.
The contact form on Vercel opens the visitor's email app (there is no server to
receive enquiries). Editing `frontend/` code needs no extra step — it is picked
up by the same Vercel build.

#### Deploying to Render (one blueprint)

`render.yaml` at the repo root describes the whole service: Node web service
in the Singapore region, `rootDir: backend`, a 1 GB persistent disk at
`/var/data`, HTTPS, health check, and auto-deploy on push. (Persistent disks
need a paid instance — `starter` is configured.)

1. Render dashboard → **New → Blueprint** → choose this repository (grant
   Render access to the private repo when asked).
2. Render prompts for `KIPL_OWNER_PASSWORD`, `KIPL_EDITOR_PASSWORD` and
   `KIPL_HR_PASSWORD`. Pick fresh passwords — they are not stored in the repo.
   On the very first start (no accounts yet) the server creates the three
   accounts from them; afterwards the variables are ignored, so changing them
   later does not reset anyone (use `seed:users -- --reset` for that).
3. Open `https://<service>.onrender.com/admin/`, sign in, change the passwords.
4. Add `kipl.co` / `www.kipl.co` under **Settings → Custom Domains** and update
   DNS as Render instructs.

## Deployment (Vercel)

The site is a plain static build with no build command, but the actual
files live in `frontend/`, not the repo root — so `vercel.json` sets
`outputDirectory: "frontend"` to tell Vercel where to serve from. Without
this, Vercel serves the repo root by default, finds no `index.html` there,
and every route 404s. `.vercelignore` excludes `docs/` (~50MB of
full-resolution source images that are reference material, never meant to
be deployed) to keep uploads fast.

## Local preview

No build step — just serve `frontend/` as static files:

```bash
cd frontend
python -m http.server 8791
```

Then open `http://localhost:8791`.

**Cache-busting while developing:** every `<link rel="stylesheet">` and
`<script src>` pointing at `css/` or `js/` carries a shared `?v=N` query
string (e.g. `css/base.css?v=1`). `python -m http.server` sends no
cache-control headers at all, which lets browsers silently serve a stale
copy of a CSS/JS file after you've edited it — a plain refresh (even
Ctrl+Shift+R, sometimes) isn't reliable, only a cache-cleared/private
window is, and that's easy to forget mid-session and chase a "fix" for
what's actually just a stale tab. **Bump `?v=N` by one, across all five
HTML pages, every time you edit any file in `css/` or `js/`** — that
forces every browser to treat it as a new URL and fetch it fresh, no
private window needed. It's one shared number for all assets on all
pages (not per-file), so bumping is a single find-and-replace. Google
Fonts/CDN `<link>`/`<script>` tags don't need this — only local
`css/`/`js/` files.

## Adding pages

`index.html`, `services.html`, `about.html`, `projects.html`, and
`contact.html` are all built. A future new page goes directly in
`frontend/`, next to the others, reusing
`css/` and `js/` as-is: shared styling lives in `css/components.css`
(nav, hero, footer, buttons, the mosaic-reveal effect, the page
transition), page-specific layout gets its own `css/<page>.css` (see
`home.css`/`services.css`/`about.css` for the pattern). Every page also
needs the same inline `<head>` script (scroll-restoration +
nav-transition-cover handoff — copy it from `services.html` or
`about.html`, *not* `index.html`, which has no nav-transition-cover
concerns of its own but does carry the Home-only preloader markup), the
`.page-transition` div right after `<body>`, and the same `?v=N` on its
own `css/`/`js/` links (see "Cache-busting while developing" above).

About's dropdown (Mission & Vision / MD's Desk / Our Team) is a
reference pattern worth reusing if a future page needs the same
"single page, multiple sections, jump to one from anywhere on the site"
structure — see `css/components.css`'s `.nav__item--dropdown` and
`js/main.js#initNavDropdowns`.
